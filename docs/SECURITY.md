# Security boundaries

RelayForge is a controlled reliability lab. Its safeguards are scoped to this application; it does not claim production certification.

## Enforced by the application

- Workspace API routes require an authenticated application session. Every workspace query and mutation is scoped to that account's stable ID.
- Accounts use email/password credentials. Passwords use randomly salted scrypt hashing. Authentication is established by the application's session cookie rather than browser-supplied identity headers.
- Session tokens are random, expire after seven days, and are stored only as SHA-256 hashes. Cookies are HttpOnly, SameSite=Lax, and Secure in production; sign-out revokes the session.
- The Security workspace uses a separate random public session ID. That identifier cannot authenticate a request, and API responses exclude token hashes. The list returns at most 50 active sessions with the current one first, the total active count, and the latest 20 security events. Last request timestamps are written at most once per minute; they do not identify a device or establish user presence.
- Revoking another session or all other sessions requires a valid authorizing session and account ownership. The current session uses the existing Sign out control. Foreign and missing session IDs return the same generic result. Expired tokens cannot authorize changes.
- Password changes verify the current password, require a different 12–128 character replacement, and atomically replace the password hash and every old session with one fresh session and an audit event. The write rechecks both the authorizing session and verified password hash after asynchronous hashing. Sign-in also rechecks its verified hash before creating a session, so verification racing with password rotation cannot revive an old password.
- Security mutation attempts have a separate persistent limit of five per account per ten minutes, shared by revocation and password changes. Password and revocation writes roll back with their audit event on a database error. Submitted passwords and raw session tokens are absent from audit messages and response JSON.
- Authentication attempts use persistent ten-minute counters: ten per normalized email and 100 across the application. This bounds password-hashing work in the current single-database deployment; larger deployments need reviewed abuse controls.
- Registration, sign-in, sign-out, and dashboard mutations require the same origin. JSON actions have strict runtime validation and bounded request size and nesting.
- Receiver envelopes require a timestamped HMAC signature. Signing keys stay in server-side storage and are excluded from API responses.
- Immutable events, database uniqueness constraints, lease tokens, and receiver effect deduplication protect distinct parts of the delivery lifecycle.
- Only built-in destinations are accepted. The delivery processor does not fetch arbitrary URLs.
- The standalone worker uses the same ownership-scoped processor, conditional claims, and completion tokens as request pumping. Its heartbeat informs the dashboard's observed processing mode; it does not grant authorization or replace lease protection.
- Recovery batch requests require the same origin and an authenticated session. They accept at most 20 unique event IDs with their expected cycles. Eligibility is checked inside the write transaction; changed, leased, completed, inaccessible, and guide-managed records are skipped without exposing another account's state.
- Replay state and its audit entry are committed together. A stale selection cannot reset a newer cycle. Recovery Lab receiver settings and event replay are restricted to the account's persisted guide actions; general send, receiver-change, and replay actions cannot bypass those controls.
- The unified audit API scopes both delivery and security records to the authenticated account. Strict query bounds reject unknown and duplicate parameters. Shareable dashboard URLs include filters and event identifiers, and never include payloads or credentials; signing in preserves only a validated local return path.
- API request IDs are generated by the server and cannot authenticate or select another account. Error codes separate credential verification failures from expired sessions. Unexpected exceptions return a generic message; their logs exclude submitted credentials, exception text, stack traces, payloads, and arbitrary client-provided IDs.
- Command palette event results use the same authenticated history API and ownership checks as Deliveries. Search text is transient component state; the palette exposes navigation destinations. Login and Security cooldown feedback uses bounded server retry metadata, while the existing persistent counters still enforce limits.

Deploy behind HTTPS and keep `DATABASE_PATH` on persistent storage. Treat the SQLite file and backups as sensitive: they contain account information, password hashes, sessions, signing keys, and delivery payloads. Never publish the local database or real credentials in the repository.

The worker is a trusted local process with direct database access; it does not authenticate through a browser session. Run it under a restricted operating-system account with the required storage permissions, using the same database as the web process. Supervise it independently of the web server. Graceful shutdown waits for an ongoing pump, while forced termination relies on lease expiry and a subsequent processing pass for recovery. A recent heartbeat indicates a recent database write, not proven queue health or availability.

## Dependency verification

```sh
npm audit --omit=dev --audit-level=high
npm audit
```

Audit results depend on the resolved dependency versions and the advisory database at the time of the check. See [Validation](VALIDATION.md) for the current recorded results. Development packages can contribute code to generated bundles, so review the full audit as well as the production dependency audit.

On **2026-10-13**, the production dependency audit reported zero findings. The full audit reported five high findings through `braces` → `micromatch` → `fast-glob` → `@next/eslint-plugin-next` → `eslint-config-next`. These belong to the lint dependency chain; the application APIs do not accept user-supplied glob patterns. Track the upstream [braces advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) and rerun the full audit when updating lint dependencies.

Review suggested dependency changes before applying them. A forced fix can introduce a breaking downgrade or change unrelated parts of the runtime. Track upstream fixes, review changed dependencies, and rerun tests and build after an upgrade.

## Current limits

Email verification, password recovery, signing-key encryption and rotation, distributed abuse controls, external destination validation, and reviewed worker operations remain future work. The local worker provides autonomous processing for controlled receivers, but does not establish production monitoring, high availability, or external delivery. Review these boundaries before offering accounts to the public. See [the architecture](ARCHITECTURE.md) for the implemented trust model and [the roadmap](ROADMAP.md) for bounded next steps.
